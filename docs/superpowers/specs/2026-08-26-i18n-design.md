# Internationalisation with English and German — design

Date: 2026-08-26
Issue: [#20 M2-3](https://github.com/beyonddemise/matter-manager/issues/20)
Status: proposed

## What this establishes

Every user-visible string in `packages/web` is already wrapped in `msg()` — M2-2 required
that from its first line. What does not exist yet is anything that *does* something with
those wrappers: no catalogue, no German, no way to choose a language. This story adds the
machinery, and in doing so fixes the pattern that M2-4 through M3 will copy.

Out of scope: translating anything outside `packages/web` (there is no other user-facing
surface yet), and persisting the preference to the user profile — the `profile.locale`
field exists in the data model but the document itself arrives with M4-5.

## The three scenarios, and what each one forces

| Scenario | What it forces |
|---|---|
| Browser reports `de-DE` → German | Negotiation matches on the primary subtag, not the full tag |
| Browser reports `fr-FR` → English | An unmatched language falls back to the source locale, never to an empty catalogue |
| Explicit preference wins, no reload | **Runtime mode**, not transform mode |

The third is the load-bearing one. `@lit/localize` has two output modes and they are not
interchangeable:

- **Transform mode** compiles one bundle per locale with the strings inlined. It is faster
  at runtime and produces smaller output, and changing locale means loading a different
  bundle — a navigation. That directly contradicts "switching locale does not reload the
  page".
- **Runtime mode** ships one bundle, loads a locale module on demand, and re-renders
  subscribed components in place.

Runtime mode it is, and the cost is accepted: the source-locale strings ship in the bundle
alongside the loaded catalogue, and `msg()` is a function call rather than a compile-time
substitution.

## Locale negotiation is a pure function

```ts
// packages/web/src/i18n/locale.ts
export type Locale = 'en' | 'de'
export type LocalePreference = 'auto' | Locale

export function negotiateLocale(
  preference: LocalePreference,
  browserLanguages: readonly string[],
): Locale
```

`navigator.languages` is passed in rather than read, exactly as `scheme.ts` takes a storage
supplier rather than reaching for `localStorage`. The consequence is that the part which can
be *wrong* — subtag matching, precedence, fallback — is tested in Node with a fixture table,
at the same rigour as `packages/core`, and needs no browser to prove.

Matching is on the primary subtag, case-insensitively: `de-DE`, `de-AT`, `DE` and
`de-DE-1996` all yield `de`. Precedence follows the browser's own list, so
`['fr-FR', 'de']` is German — the first *supported* entry wins, not the first entry.

`auto` is the default and the fallback for anything unrecognised, on the same reasoning
`scheme.ts` gives for `system`: it is the one answer that is never wrong.

## The preference is stored the way the scheme preference is

`localStorage`, key `matter-manager.locale`, values `auto | en | de` — deliberately the same
three values as the `profile.locale` field in the data model, so M4-5 lifts the preference
into the profile document without a migration or a value mapping.

The guarded-storage read and write are extracted to `src/preferences.ts` and both
`scheme.ts` and `locale.ts` use them. This is not tidying for its own sake: the guard has a
subtlety that is easy to copy wrongly — the storage *supplier* must be invoked **inside** the
`try`, because on a hostile origin the throwing site is the `localStorage` property access
itself, not `getItem`. A second hand-written copy of that pattern is a second chance to get
it subtly wrong, and [#70](https://github.com/beyonddemise/matter-manager/issues/70) will
want a third.

## The document language follows the locale

`document.documentElement.lang` is set whenever the locale activates. `index.html` hard-codes
`lang="en"`, and leaving it there while rendering German is not cosmetic: it is what screen
readers use to choose a voice, what the browser uses for hyphenation and spell-checking, and
what `:lang()` selectors match.

## Components re-render through `updateWhenLocaleChanges`

The package sets `experimentalDecorators: false`, so the `@localized()` decorator is
unavailable. Its non-decorator equivalent, `updateWhenLocaleChanges(this)`, goes in each
component's constructor. Every component that renders a `msg()` needs it; a component that
forgets simply keeps its old strings while its neighbours change, which is a silent failure
and therefore gets a test.

Route labels are already thunks — `label: () => msg('Devices')` — so they re-evaluate on the
shell's re-render with no further mechanism.

## Generated code is committed, and drift is a CI failure

`lit-localize build` generates the locale modules; `lit-localize extract` updates the XLIFF
catalogue. Both outputs are committed, because a checkout must build without a code
generation step.

Committed generated code goes stale silently, so `npm run check:i18n` re-runs both commands
and fails if the working tree changed. A developer who adds a `msg()` without extracting sees
a red build naming the file, not a missing German string discovered by a user months later.

`packages/web/src/generated/**` is excluded from the coverage gate. It is not hand-written
logic and its statement count would move the number without anyone having tested anything.

## No unwrapped strings, checked rather than asserted

The issue's "done when" is *no user-visible string literal appears in any component*. That is
a property of code that does not exist yet as much as of code that does, so it needs a check
rather than a review habit.

`scripts/check-i18n.mjs` scans `html` tagged templates in `packages/web/src`, removes the
`${…}` interpolations, and reports any remaining text content or user-visible attribute
(`label`, `placeholder`, `title`, `alt`, `aria-label`) that contains a word.

It is a lint heuristic, not a proof — it cannot see a string built in a helper function and
returned into a template. It is documented as such. What it does reliably catch is the actual
failure mode: someone types visible text straight into markup. The checker is proved able to
fail before it is trusted, per lesson L8.

## A settings surface, because a preference needs somewhere to live

The M2-2 design said the navigation "grows when M2-3 adds a settings surface", and this is
that. A `/settings` route and a `settings-view` with one control: a language picker offering
*Automatic*, *English* and *Deutsch*.

Each language is named in its own language, which is the convention for language pickers and
the only one that works — a user who has landed in a language they cannot read must still be
able to find their own.

Colour scheme is deliberately *not* moved here. It stays in the header where M2-2 put it, and
theme/palette selection remains [#70](https://github.com/beyonddemise/matter-manager/issues/70).

## Files

```
lit-localize.json                          runtime mode, en → de
packages/web/xliff/de.xlf                  the catalogue; targets hand-written
packages/web/src/generated/                lit-localize output, committed, drift-checked
packages/web/src/preferences.ts            guarded localStorage read/write, shared
packages/web/src/i18n/locale.ts            pure negotiation + the preference
packages/web/src/i18n/localization.ts      configureLocalization wiring, activateLocale
packages/web/src/views/settings.ts         the language picker
scripts/check-i18n.mjs                     no unwrapped user-visible literals
```

## Testing

| Unit | How | Environment |
|---|---|---|
| `negotiateLocale` | fixture table over preference × browser languages | node |
| preference read/write | supplier that throws, returns junk, returns valid | node |
| `activateLocale` | sets `documentElement.lang`, resolves, is idempotent | browser |
| German actually renders | activate `de`, assert a translated string in the shell | browser |
| every component subscribes | switch locale, assert *each* view's text changed | browser |
| settings picker | selecting a language switches without a navigation | browser |
| the checker fails | a planted unwrapped literal is reported | node |

## What could go wrong

**A component renders before its catalogue loads.** `setLocale` is asynchronous. `main.ts`
awaits it before the first render matters; a component mounted later renders the source
locale for one frame and then updates. Acceptable, and the alternative — blocking the whole
shell on a network fetch — is worse.

**`configureLocalization` is called twice.** It throws. It lives in exactly one module and is
called at import time, which module caching makes once per page. Tests import the same module
rather than re-configuring.

**The German is wrong.** No test can catch a plausible mistranslation. The catalogue is small
enough to read, and the repository owner is a native speaker.
